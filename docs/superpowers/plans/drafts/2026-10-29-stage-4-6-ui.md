**Shared rules for every task:**
- Frontend types come only from the generated `schema.d.ts`; each task that adds a backend route commits the regenerated `frontend/openapi.json`. Routers are new files under `api/routers/` (discovered by `include_routers`), hold no logic, and use `ProjectDep` and `ServicesDep`.
- No literal the backend owns is copied into the frontend: severity order, status sets, bounds and wording come from the API (a 422's message is shown as is). Labels for display are the only frontend constants.
- A page refreshes by invalidating its TanStack queries on the matching events from `useProjectEvents` (incidents on `incident.*` and `signal.raised`, the Dashboard also on `results.collected`), never by polling.
- Nothing on screen pretends to work: a control whose route is not on `main` is not shown, not disabled with a promise.
- Tests: backend through the app's `TestClient` pattern with fakes from `tests/fakes/` (no network, provider or Docker); frontend with vitest and the existing `renderPage`/query helpers.

### Task 1: Usage: the route, the price on the model, the page

**Files:** new `backend/src/mlops_agents/providers/usage.py` (the price parsing, `cost_usd`, the usage sum), `providers/listing.py` (`ListedModel` reads `pricing`; `RemoteModel` gains the price), `providers/models.py` (`ModelEntry.price`), `providers/service.py` (store the provider price on add, verify and `list_remote_models`; `set_price`), `api/routers/models.py` (`PUT /api/models/price`), new `api/routers/usage.py`; in `backend/tests/fakes/fake_openai.py` an optional `pricing` per listed model, its own lines only; tests `backend/tests/providers/test_usage.py`, `test_prices.py`, `tests/api/test_usage.py`; `frontend/src/pages/providers/ModelsTable.tsx` (the price cell and editor), new `frontend/src/pages/usage/route.tsx` (nav `{ area: "app", label: "Usage", order: 25 }`), `UsagePage.tsx` and tests; `frontend/openapi.json`.

**Interfaces:** consumes `ModelPrice`, `UsageRow`, `UsageView` (contracts), the price columns, `llm_calls` of every project (`Databases.project`), the projects list. Produces `cost_usd`, `ModelEntry.price`, `GET /api/usage?since=`, `PUT /api/models/price`.

**Notes:**
- **Price unit:** OpenRouter's `pricing.prompt` and `pricing.completion` are strings in USD per token; `*_per_mtok = float(value) * 1_000_000`, converted in one function in `usage.py`. A missing, non-numeric or negative value means no provider price.
- **A user price is never overwritten:** the provider price is written only when the stored price is null or `source="provider"`. The route's body is a router-local model (`extra="forbid"`: `address`, and `price`, either null, which clears the user price, or two finite numbers `>= 0`); the server sets `source="user"`, a client never sends `source`. The address is in the body, as `PUT /api/models/context-window` takes it (OpenRouter wire IDs hold `/`).
- **Usage sum:** one query per project over `llm_calls`, grouped by agent, `model_address` and week; a null token count adds 0; `week_start` is the Monday of the call's UTC date; cost comes from the one function `cost_usd(prompt_tokens, completion_tokens, price)` (`(prompt * prompt_per_mtok + completion * completion_per_mtok) / 1e6`; Stats uses it too) with the model's current price, `None` when the model has no price (or was deleted), and that address listed in `unpriced_models`.
- The page (app level) shows tokens and $ per project, agent and week; with no price it shows tokens only (2026-10-29).

**Tests (stop condition):** the per-token string `"0.000003"` becomes `3.0` per million; a listing with pricing stores a provider price on add and on `list_remote_models`; a user price survives a later listing; the price route sets and clears, 404 for an unknown model, works with an address holding `/`, refuses a body with `source` or a negative price; usage sums two projects' calls by agent, model and week, counts null tokens as 0, puts calls on both sides of a Monday 00:00 UTC in two weeks, computes cost with a price and `None` without, lists the unpriced model; `since` filters; the page renders rows, totals and the "tokens only" state. Full suites; CI green.

**PR:** early PR from `plan/stage-4-6-ui-task1` into `main` (`AGENTS.md` rule 5): stats task 3 consumes `cost_usd` and `ModelEntry.price`.

### Task 2: The Dashboard: route and page

**Files:** new `backend/src/mlops_agents/monitoring/dashboard.py` (the builder), new `api/routers/dashboard.py`, `api/services.py` (its own lines: the builder's construction), tests `backend/tests/monitoring/test_dashboard.py`, `backend/tests/api/test_dashboard.py`; new `frontend/src/pages/dashboard/route.tsx`, `DashboardPage.tsx` and its parts and tests; `frontend/openapi.json`.

**Interfaces:** consumes `Handoffs.current`, `Tracking.query(what="models")` (`ModelSummary.production_version`), `Incidents.list`, `Incidents.signals`, `ACTIVE_STATUSES`, `stages_of`, `Expectations.states`, `StatusBoard.snapshot`, `Settings.mode`, `Results.query`, `Baseline.available`, I39's types; produces `GET /api/projects/{id}/dashboard` → `DashboardView`.

**Notes:**
- `stages` and `edges` come from the current handoff's `pipeline` and `edges`; no handoff gives empty lists and the page says the map appears once onboarding is approved.
- `StageStatus.status`: `incident` when an active incident (`ACTIVE_STATUSES`) has a signal whose subject belongs to the stage (`stages_of`, the same match grouping uses), `late` when an expectation in state `late` or `silent` belongs to it, else `ok`; `unknown` when nothing is known about the stage. `incident_ids` lists those incidents.
- `incidents_by_severity` counts active incidents with every `Severity` key present (zero included).
- `models`: one `ModelCard` per handoff `ModelSpec` (several models per project, S5 change 6); `latest_metrics` is the latest stored result value per check of that model (`Results.query(model=..., latest=True)`, keyed by `check_id`, values only); `open_incidents` counts active incidents with that `model`.
- `at_risk`: expectation states `due`, `late`, `silent`. `agents`: `AgentActivity(agent, state, doing=task.title or None)` from the status board.
- `heartbeat_reachable` is `settings.mode is RunMode.SERVER`; when false the page shows the local-mode notice of S4 §3b (an app that is down pages nobody, and the heartbeat cannot be reached from outside).
- `baseline_available` is `Baseline.available(project_id)`, never a second rule; when false the page says the team's own monitoring is not readable yet, so comparisons with it are unavailable (S4 §10).
- The page is the first project page: route `/projects/:projectId/dashboard`, nav `{ area: "project", label: "Dashboard", order: -10 }`, so the existing `ProjectHome` redirect (which picks the lowest order) lands on it; `project-home/*` stays as it is. Stage cards link their incidents to the incident page only once task 3 is in; until then they show the count.

**Tests (stop condition):** builder with fake stores: a handoff with three stages and an open incident whose signal subject is an output of stage 2 marks stage 2 `incident` with its ID and the others `ok`; a `silent` feed expectation marks its stage `late`; no handoff gives empty stages and models; severity counts include zeros and leave out resolved, closed and merged incidents; two models each get their card and incident count; local mode gives `heartbeat_reachable` false; `baseline_available` follows a fake `Baseline`. Route: 200 with the view, 404 for an unknown project. Page: renders stages, edges, model cards, severity counts, at-risk expectations, agents; the local-mode notice in local mode; the empty-handoff message; an `incident.opened` event refetches. Full suites, ruff, pyright, lint; CI green.

### Task 3: Inbox incidents, the incident page, verdicts and the miss report

**Files:** `frontend/src/pages/inbox/InboxPage.tsx` (one incidents section; its body in a new `frontend/src/pages/incidents/IncidentList.tsx`), new `frontend/src/pages/incidents/route.tsx` (path `/projects/:projectId/incidents/:incidentId`, no nav entry), `IncidentPage.tsx`, `Timeline.tsx`, `VerdictButtons.tsx`, `MissReportDialog.tsx` and tests; a backend test pinning notifications' `INCIDENT_PATH` to this route's path.

**Interfaces:** consumes the incident routes (list, get, signals, timeline, acknowledge, close), stats task 1's verdict and miss routes, promotion task 2's report route only once it is on `main` (not needed here). Produces the pages.

**Notes:**
- The Inbox shows active incidents in the order the route returns them (ranked by severity in the backend, one source), each with severity, category, cause, age, its verdict if any, and Acknowledge (person only, S4 §5). Approvals stay as they are.
- Snooze is not in this task: it ships in task 8 once incidents task 7 has merged.
- The incident page shows category and subtype, severity, status and every lifecycle timestamp, cause, `held`, `resolved_offline`, `reopened_count`, `merged_into` (a link), the signals with their source records, related PRs and issues, the verdict, and the timeline (the incident's timeline route, newest first, paged with `before`). Event types it labels: every stage 4-5 type with an incident subject, including `incident.wake_skipped` (decided point 10), `incident.suspect_linked`, `incident.hold_recorded`, `hook.ran`/`hook.failed`, `rule.satisfied`, notifications and verdicts. A signal's `detail` and a note are shown as text, never as HTML.
- `VerdictButtons`: real issue, not an issue, wrong type (then the right category and optional subtype), optional note; used on the incident page and on each Inbox row (S4 §11). After a verdict the incident may close (the backend decides); Close is a separate person action on the page.
- The miss report (description, optional category, when it happened) is a dialog on the Inbox.

**Tests (stop condition):** Inbox lists incidents in the route's order and acknowledges one (the request is sent, the row updates); an `incident.opened` event refetches; the incident page renders the fields above, a `wake_skipped` and a `suspect_linked` entry in the timeline, and a `detail` holding `<script>` as plain text; the timeline loads its next page; each verdict value posts the right body, wrong type requires a category; a refused verdict shows the server's message; the miss report posts and closes; an unknown incident shows not found; the notifications link path matches the route. Full suites; CI green.
