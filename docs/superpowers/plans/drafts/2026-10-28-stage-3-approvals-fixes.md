## What is wrong, in the code

- `ApprovalsService.decide` commits the status (`ApprovalStore.update_status`, which then tells the observers), then `_record` writes the part, then the audit record and the event, then `_resume_when_none_pending` or `stop`. A process death in between leaves the approval decided, the part `pending`, no records, and the turn `waiting`: `SessionStore.recover` only expires pending approvals of turns that are not waiting, and resumes nothing.
- The same "rewrite the part, then `record_decisions`" is written three times: `ApprovalsService._record`, `stop_waiting_turn` (`runtime/waiting.py`) and the expiry block of `SessionStore.recover`. Their order (part first) also loses the records when the process dies after the part, and nothing records that an approval's records and card were written, so nothing can find one that is not.
- Nothing records who decided an approval (user or system), so a repair cannot write the true actor.
- A turn that ends without waiting (`TurnEnds.end`) touches no approval, so an approval created while it ran stays pending. `stop_waiting_turn` sweeps only a `waiting` turn. `SessionManager.stop` never calls `_ensure_recovered`, so a Stop sent first after a restart stops a turn whose decided approval was never repaired.
- A rejected stall calls `SessionManager.stop`, which starts with `_check_agent`: a `chat: false` agent raises `agent_cannot_chat` after the rejection is stored.
- `_recovery_lock` in `SessionManager` is one lock for every project; the `ApprovalObserver` docstring forbids blocking and calling back on every `decided`, broader than the code (#380 items 3 and 1).

    CHECK (decided_by IS NULL OR decided_by IN ('user', 'system'));
  ALTER TABLE approvals ADD COLUMN settled_at TEXT;

**Implementation notes:**
- **Two markers, two jobs.** `settled_at` says "records and card are written" and is how the repair (task 2) finds every unfinished approval, for any turn, without scanning messages: the partial index `approvals_unsettled` holds only decided approvals not yet settled, so the startup query touches a handful of rows, whatever the history. The existence checks below stay, for the states `settled_at` cannot tell apart: a crash after the audit record and before the event, or after both and before the card. They run only while settling an approval, with one index probe each.
- **Exactly once without a flag per record.** The audit record and the event are two commits, so no single flag makes both exactly-once; `record_decisions` checks before it writes. Inside `async with store.settling(project_id)`, per approval: skip the event when `events` has a row with `type = 'approval.decided'` and `subject_id = approval.id`; skip the audit record (tool approvals only) when `audit` has a row with `action = 'approval'` and `json_extract(detail, '$.approval_id') = approval.id`. An approval is decided once, so one of each is the rule; a crash between the audit record and the event leaves the audit record, and the next call writes only the event. Write the audit check's `json_extract(detail, '$.approval_id')` and `action = 'approval'` as literal SQL text matching the index exactly, not as SQLAlchemy `func.json_extract(...)` and `== "approval"`, which bind the path and the constant as parameters that SQLite cannot match to the partial expression index (the quirk `store.py` handles with the literal `_PENDING_STALL`); the same for the `approvals_unsettled` query in task 2. `json_extract` is deterministic, so SQLite accepts it in an index.
  ```python
  async with store.settling(project_id):
      for a in approvals:
          if audit_log is not None and a.kind == "tool" and not await _has_audit(engine, a.id):
              ...write the audit record, actor a.decided_by or "system"
          if event_log is not None and not await _has_event(engine, a.id):
              ...write the event, after the audit record
  ```
- The lock covers only these checks and writes, never the card rewrite: `rewrite_part` takes the session lock (`SessionManager.update_message`), and `stop_waiting_turn` holds the session lock and then settles, so holding both in opposite orders would deadlock.
- **Callers.** `ApprovalsService.decide` and `cancel` call `settle_decisions` with `rewrite_part=self._sessions.update_message` (bound to the project); `stop_waiting_turn` with its store and hub; the expiry block of `recover` with `SessionStore.message` plus `update_message` (no publish). The three copies are removed. A stall writes no audit record (`record_decisions` already skips it); its card is rewritten like any other.
- **Seeded rows.** Production never inserts an already-decided approval: the gate and `create_stall` always create `pending`, and only `update_status` and the sweeps decide. `ApprovalStore.create(..., status=...)` therefore does not branch for it. Tests that seed a decided row do it through the shared helper in `tests/agents/approval_env.py` (a `seed_decided_approval` that creates it and sets `settled_at` and `decided_by` with one SQL update), so a seeded row is not re-told and re-settled by a later `ensure`.
- **Old rows.** The migration marks every already-decided approval settled, so the first start does not re-settle history; their `decided_by` is NULL, which the code treats as unknown and records as `system`. Only approvals decided after the migration carry the true actor.

**Tests (stop condition):** every race and repair test in this plan builds one `ApprovalStore` and passes it to the manager, the gate and the service, as `build_services` does (`SessionEnv.approval_store`); a second store has its own settle lock and observers, so such a test would prove nothing (the existing `test_decision_racing_with_stop_stop_wins_decision_gets_409` builds a second one and is changed to use the shared one).
- `record_decisions` twice for one approval writes one audit record and one `approval.decided` event; with the audit record present and no event, only the event is written; with both present, nothing; a stall writes its event once and no audit record.
- `settle_decisions` writes the audit record and the event before the card, and sets `settled_at` last: with a `rewrite_part` that cancels, the records exist, the card is `pending` and `settled_at` is null (a call again writes no record, settles the card and sets `settled_at`); with a log that cancels on its first call, no card was written and `settled_at` is null.
- `decided_by`: a user's approve and reject store `user`, `cancel` stores `system`, the Stop sweep `user`, expiry `system`, each in the same update as the status; the audit record's `actor` is that value; a row with a null `decided_by` is recorded as `system`.
- Two `settle_decisions` of the same approval at once (`asyncio.gather`): one audit record, one event, a settled card, one `settled_at`.
- Schema: inserting or updating `decided_by` to anything but NULL, `user` or `system` fails the CHECK; NULL, `user` and `system` pass.
- Migration: applies to a fresh database and to one at version 4 with a pending, an approved and an expired approval: the decided ones get `settled_at` (`decided_at`), the pending one none, `decided_by` is null for all; `PRAGMA foreign_key_check` is clean; `EXPLAIN QUERY PLAN` shows `approvals_unsettled` for the unsettled query, `events_type_subject` for the event check and `audit_approval_id` for the audit check, no `SCAN` of `events` or `audit`.
- No deadlock: `settle_decisions` from `stop_waiting_turn` (session lock held) racing a live `decide` of another approval of the same project, under a timeout.
- Behavior of live `decide`, `cancel`, Stop and recovery expiry is unchanged: the existing approval, stop and recovery tests pass, adjusted only for the order of the writes.
- `uv run pytest`, `ruff check`, `ruff format`, `pyright`; CI green on every job.

**Interfaces:** Consumes task 1's `settle_decisions`, `settled_at`, `decided_by`. Produces:
- `ApprovalStore.unsettled(project_id) -> list[ApprovalRecord]`: decided approvals (any turn) with `settled_at` null, ordered by `created_at`; the query's `status <> 'pending' AND settled_at IS NULL` is literal SQL text matching `approvals_unsettled`.
- `ApprovalStore.of_waiting_turns(project_id) -> list[ApprovalRecord]`: every approval, any status, of a turn whose status is `waiting`.
- `ApprovalStore.retell_decided(records)`: tells the `decided` observers again.
- `ProjectRecovery` (`runtime/repair.py`), held by `SessionManager`: `ensure(project_id)` (what `_ensure_recovered` is today), `recover_only(project_id)` (close-time: `SessionStore.recover`, logged on failure, never repairs), `recovered() -> set[str]`, `cancel(project_id=None)` (cancels and awaits the repair tasks), `forget(project_id=None)`. It owns the recovered set, the per-project locks and the repair tasks.
- `repair_unsettled_approvals(project_id, *, unsettled: list[ApprovalRecord], approval_store, store: SessionStore, databases, audit_log, event_log, rewrite_part, stop_turn, resume_turn) -> None` in `runtime/repair.py`; `unsettled` is the snapshot `ProjectRecovery.ensure` took inside the recovery lock. `SessionStore.recover` does not call it.
- `AgentSessions.stop_turn(project_id, session_id, turn_id) -> None`: stops that waiting turn without the chat check; nothing happens when the turn is not waiting.

**Implementation notes:**
- **`sessions.py` does not grow** (389 lines on `main`; rate-limits pushes it past 400). The recovery code moves to `ProjectRecovery`: the two attributes `_recovered_projects` and `_recovery_lock` (as on `main` before rate-limits; find them by name after it merges), `ensure_recovered` and `_ensure_recovered` (which become a one-line delegate `await self._recovery.ensure(project_id)`, and its call sites), the recover-and-log block of `_recover_and_clear_project` (which becomes `await self._recovery.recover_only(project_id)` after `forget`) and the `_recovered_projects` uses in `close`. The lines are found by name, because rate-limits moves them before this plan starts. What `sessions.py` gains is `stop_turn`, the `_stop` split and the `ProjectRecovery(...)` construction; the PR description gives `wc -l sessions.py` before and after, and it must not be larger. (`ProjectRecovery` gets `rewrite_part=self.update_message`, `stop_turn=self.stop_turn`, `resume_turn=self.resume_turn`, whose signatures already match.)
- **Recovery has two parts, and only the first runs under a lock.** `SessionStore.recover` is unchanged (running turns, expiry). The repair is a separate step `ProjectRecovery.ensure` runs after it marks the project recovered and outside the recovery lock: it tells observers, and a proposal kind's `apply` may call back into `AgentSessions` (onboarding's handoff kind posts the kickoff through `sessions.post`, which calls `ensure` and would wait on a lock recovery holds); `resume_turn` does the same. Close-time recovery (`close`, `close_project`) calls `recover_only`: it never re-tells, applies, settles or resumes.
- **One recovery lock per project (#380 item 3).** `ProjectRecovery` keeps `dict[str, asyncio.Lock]`, created with `setdefault` and dropped only by `forget()` with no project (the `close()` case), never for one project (dropping a lock another caller still holds would let two recoveries of that project run at once). A slow expiry observer of one project no longer delays another's first use.
  ```python
  async with self._lock_for(project_id):
      if project_id in self._recovered:
          return
      await self._store.recover(project_id, ...)
      snapshot = await self._approval_store.unsettled(project_id)   # before the project counts as recovered
      self._recovered.add(project_id)
      # outside the lock; the repair is a task owned here and works on the snapshot only
      repair = asyncio.create_task(self._repair(project_id, snapshot))   # logs its own failure, never raises
      self._repairs[project_id] = repair
  await asyncio.shield(repair)   # a cancel of this caller cancels only its wait
  ```
  (`_repair` runs `repair_unsettled_approvals(...)` inside `try/except Exception: logger.exception(...)`; the `create_task` sits inside the lock only so no second caller starts another; the repair itself takes no recovery lock. Later callers return at the fast path and do not wait for the repair: an observer's `apply` that calls `sessions.post` would otherwise wait on the repair that waits on it.)
- **The repair is not tied to the first caller's request.** Run inline, a cancelled first request would stop it halfway and nothing would run it again until the next start (the project is already marked recovered). `SessionManager.close_project` and `close()` call `ProjectRecovery.cancel` first, before `_workers.cancel`: a repair about to call `resume_turn` could otherwise start a new worker after the workers were cancelled, which would write while the database closes. A repair cut at close is repeated at the next start; every step is idempotent. It is not `@shielded` (`runtime/shielded.py`): that would make the first caller's cancel, and shutdown, wait for a slow proposal `apply`.
- **The repair**, in this order, each step as the live path orders it (observers, then records, then the card, then the turn):
  1. The snapshot: every decided approval, on any turn, whose records or card are not both written, found without a scan of messages or events (the partial index). It is read inside the project's recovery lock, before the project is marked recovered, and the repair re-tells and settles that snapshot only. Every live decision path calls `ensure_recovered` before it commits (the recovery wait is the first caller's; later callers pass once the project is marked), so a decision made after the snapshot is a live one and is never in it: `ApprovalsService.pending`, `decide` and `cancel` (`approvals/service.py:44,74,91`), `SessionManager.get`, `_enqueue` and `resume_turn` (`sessions.py:141,224,294`; a turn, and so a turn-end sweep, runs only after a send, a post, a get or a resume), `stop` and `stop_turn` (the `ensure` this task adds). The process died after the status commit, so the observers may not have finished: `approval_store.retell_decided(snapshot)`. This is the ownership split of the Produces list: the re-tell covers a decided approval whose observers may not have run (a proposal still `pending`: `decide` applies it once); proposals' `recover` covers a proposal `approved` with no `result`; a repeat for a proposal no longer `pending` returns `None`. Proposals' `recover` runs in `build_services`, before any turn, so by the time of the re-tell it has applied what it owns. An unsettled approval whose records are already written is told again too, which is harmless: observers are idempotent. `settled_at` cannot say whether the observers ran, so the repair does not guess.
  2. `settle_decisions` for the snapshot: the records (with the true `decided_by`), then the card, then `settled_at`. This covers every state of the crash window, for a waiting turn or a turn that ended (a Stop or an expiry that died between its writes), and it closes the stale chat card: the card's status comes from the message part (`GenericApprovalCard.tsx:111`), and the repair now rewrites every part whose approval is decided but unsettled.
  3. A turn waits only for an approval: `handle_turn_waiting` is the one writer of `waiting` (`waiting.py:191`), reached only when the graph is interrupted (`graph_run.py`), and the only `interrupt()` calls are `ApprovalGate.wait` with an approval pending (`gate.py:195`) and rate-limits' `await_stall` with its stall approval pending (rate-limits task 3); nothing else makes a turn wait (checked in `src` and in the stage 3, 4 and 5 plans). So "no approval pending" means every approval it waited for is decided, the rule `_resume_when_none_pending` already uses. For each waiting turn with at least one approval, none `pending` and none unsettled (`of_waiting_turns` grouped by turn and `approval_store.unsettled`, both read after step 2): `stop_turn` when one of its approvals is a `stall` with status `rejected` (rejecting a stall always ends its turn), else `resume_turn`. An approval still unsettled at this point is either in flight in a live decide (committed after the snapshot; that decide resumes its own turn once its observers are done) or one that failed to settle (the next start handles it); finishing its turn here would resume it before a proposal's `apply` ended. A crash between `mark_settled` and `resume_turn` leaves a waiting turn with everything settled, which this step does resume. A failing finish is logged per turn (`logger.exception`) and the next one still runs; the turn stays waiting with its card settled, and the next start finishes it.
- **Never a double resume.** The live decide and the repair both end in `resume_turn`, which acts only on a `waiting` turn with no worker running, under the session lock. A second repair (a new manager; two first calls at once, where only the call that ran `recover` repairs) finds the turn `running` or ended and does nothing. A live decide overlapping the repair (it commits after `ensure` marked the project recovered, while the repair runs) is not in the snapshot, so its observers are told once, by the live path; the settle lock and task 1's checks cover the writes, and the repair never resumes a turn that has an unsettled approval, so "observers finish before the turn resumes" holds for it.
- **`stop_turn`.** `SessionManager.stop(project_id, agent)` becomes `_check_agent` + `ensure` + `_stop(project_id, agent, turn_id=None)`; the `ensure` is new, because a Stop sent first after a restart must not stop a turn whose approvals were never repaired. `stop_turn` looks the agent up with `SessionStore.session_agent`, calls `ensure`, then `_stop(project_id, agent, turn_id=turn_id)`. `_stop` is today's body of `stop`: it calls `workers.stop` only when `turn_id` is `None`, and under the session lock it stops the waiting turn only if that turn is `turn_id` (when given). `ApprovalsService.decide` calls `stop_turn(project_id, record.session_id, record.turn_id)` for a rejected stall instead of `stop(agent)`, so a `chat: false` agent's turn ends `stopped` with no chat check; the user's Stop route keeps the check.
- **`ApprovalObserver` docstring (#380 item 1).** Replace the blanket rule with: on a user's approve or reject no lock is held, so slow work such as a proposal's `apply` is allowed there, and an observer may call `Approvals` or `AgentSessions`; Stop (the session lock) and recovery expiry (the project's recovery lock) hold a lock, and the turn-end sweep (task 3) runs inside the turn's shielded end; all three only ever give `cancelled` or `expired`, so an observer must not block or call back for those; `decided` may be told again for an approval after a crash (the restart repair), so observers must be idempotent.
- `turn.resumed` is recorded by the graph when the resumed turn runs (rate-limits), so the repair needs nothing for it.
- **Crash tests.** They simulate the process dying with an observer or log whose call raises `asyncio.CancelledError` (a plain `Exception` is caught by `ApprovalObservers.tell` and logged, and the decide would simply go on), then build a new `SessionManager`, `ApprovalStore` and `ApprovalsService` on the same databases, as a restart does. The crashed manager is dropped, never closed: a process death closes nothing, and the test must prove the restart repair, not a close.

**Tests (stop condition):** one shared `ApprovalStore`, as in task 1.

After the rebuild and `ensure`: the card is `approved` with its note, `settled_at` set, one audit record (decision approved, actor user, from `decided_by`), one `approval.decided` event, the `decided` observer was told once more (a recording observer), the turn was resumed once and ends `done` with the tool run.

### Task 3: Every turn end cancels its pending approvals; a decision only while its turn waits

**Files:** `backend/src/mlops_agents/agents/runtime/waiting.py` (`stop_waiting_turn`, new `cancel_turn_approvals`), `approvals/service.py` (`pending`), `approvals/contract.py` (`Approvals.pending` doc), `runtime/turn_end.py` (`TurnEnds.end`), `runtime/worker.py` and `runtime/sessions.py` (hand `TurnEnds` the approval store and the logs), `runtime/store/__init__.py` (`recover`), `approvals/store.py` (`update_status`, `decide`, `decidable`), `approvals/contract.py` (the `ApprovalObserver` docstring names the turn-end sweep, as task 2 wrote it); tests `backend/tests/agents/test_approval_stop.py` (new), and the existing tests that decide an approval of a turn that is not `waiting`.

**Interfaces:** Consumes task 1's `settle_decisions`, `ApprovalStore.cancel_for_turn(..., decided_by)`, `TurnEnds`, `SessionStore.set_turn`. Produces `cancel_turn_approvals(project_id, session_id, turn_id, *, decided_by, store, hub, approval_store, audit_log, event_log)` in `waiting.py`; `ApprovalStore.update_status(..., while_turn_waiting: bool = False)`; `ApprovalStore.decidable(project_id) -> list[ApprovalRecord]` (pending approvals of turns that are `waiting`); the error `approval_turn_not_waiting` (409, "The turn of this approval is not waiting for it right now.").

**Implementation notes:**
- **One sweep.** `cancel_turn_approvals` is `approval_store.cancel_for_turn(project_id, turn_id, decided_by=decided_by)` followed by `settle_decisions(...)`, where the rewrite reads each approval's own message (`ApprovalRecord.message_id`) and rewrites only the parts that exist: the agent message of a turn that has not waited yet does not hold the approval part (`handle_turn_waiting` adds it), and the sweep must not assume it does. It replaces the cancel-and-rewrite block of `stop_waiting_turn`.
- **Every turn end.** `TurnEnds.end` calls it for a `done`, `failed` or `stopped` end (not `interrupted`: recovery expires those; not `waiting`: the turn has not ended), with `decided_by="user"` for `stopped` and `"system"` otherwise, after `_store_end` (or its fallback) and before `_turn_ended`, in its own `try` that logs and never raises, like `_record_end`: the end is stored, and a sweep that fails leaves its approvals decided and unsettled (task 2's repair finishes them at the next start) or still pending (the next recovery expires them, `expire_non_waiting`). It runs after the turn task has finished, so no approval can be created after it; that is why the sweep is not in `SessionManager.stop` (a gate `create` can still commit after `stop` cancels the task). The sweep tells its observers (`decided`, `cancelled`) outside the session lock; only its card rewrite takes it (`SessionManager.update_message` or the store's rewrite under the lock the end holds). No ended turn keeps a pending approval. `TurnEnds` gets the approval store and the logs through `TurnWorkers`, which `SessionManager` builds with them.
- **The stopped message.** A `stopped` end marks the turn's agent message `stopped` when it is still `waiting` (a turn stopped before its worker ran, for example right after an approve, otherwise keeps a `waiting` message). `recover` does the same for a crash: where it already moves `streaming` messages to `interrupted`, it moves the agent message of a `stopped` turn that is still `waiting` to `stopped`.
- **A waiting turn.** `stop_waiting_turn` first stores `stopped` (`set_turn`), then sweeps (`cancel_turn_approvals`, `decided_by="user"`), then marks the agent message `stopped`, publishes, deletes the checkpoint, notifies the observers. Today it sweeps first; a crash between the sweep and `set_turn` left a `waiting` turn whose approvals were all cancelled, and task 2's repair would resume it. With `stopped` first, a crash in between leaves a stopped turn with pending approvals, which recovery already expires.
- **A decision only while its turn waits.** With `stopped` stored first, a decision committed between `set_turn` and the sweep would run the observers (a proposal's `apply`) for a stopped turn. `ApprovalStore.decide` (user approve and reject only; sweeps, `cancel` and expiry are not conditional) passes `while_turn_waiting=True`, which adds `AND turn_id IN (SELECT id FROM turns WHERE status = 'waiting')` to the same conditional `UPDATE`. A zero-row update reports `approval_not_pending` when the approval is not pending, else `approval_turn_not_waiting`. This also closes the live variant of #381 gap 1: a decision that lands while the turn is still running (before `handle_turn_waiting`) is refused instead of being committed with no resume. Existing tests that decide an approval of a running turn give the turn status `waiting` (`tests/agents/approval_env.py::add_turn` already defaults to it).
- **What the user sees, the Inbox, and who reads the list.** `ApprovalsService.pending` (the route `GET /api/projects/{id}/approvals`, `api/routers/approvals.py:28-35`, its only backend reader) listed `ApprovalStore.pending`, every pending row, so an approval showed in the Inbox as soon as the gate created it: the frontend refetches on `approval.requested` (`frontend/src/pages/inbox/usePendingApprovals.ts:49`), which the gate records right after `create` (`gate.py:165`), before `handle_turn_waiting` stores `waiting` (`waiting.py:191`). It now returns `decidable`, so an approval is listed only once its turn waits; the hook refetches on `turn.waiting` (`usePendingApprovals.ts:52`), so it appears then. Its meaning is now "the approvals the user can decide now" (the I13 line). The readers: the Inbox list (`usePendingApprovals`, `InboxPage.tsx:29`) and the Inbox badge (`useInboxBadge`, `usePendingApprovals.ts:168-174`, used by `pages/inbox/route.tsx:4` for the sidebar). Their meaning changes in two ways: neither counts an approval in the milliseconds before its turn waits, and neither counts a pending approval of an ended turn that nothing has swept yet (before: counted though undecidable). No other reader: the stage 3 pages plan only moves the hook's debounce (`2026-10-28-stage-3-pages.md:40`), rate-limits task 4's stall card renders from this list and its Inbox test stubs the route, and the stage 4-5 draft has none (the status board reads `turn_states`, `events/status.py:183`). The chat card is different: its part is written with the message at `waiting.py:186` and the turn is marked `waiting` at `:191`, a few milliseconds later (the order cannot be swapped: a decision before the part exists would leave the part `pending` for good). A click in that window answers 409 `approval_turn_not_waiting`; the card shows the message in its alert and the buttons work again (`ApprovalControls.tsx:41-44` shows `errorText` of any error). So "no frontend change" holds.
- **Every approval blocks its turn.** The guard and the every-end sweep rest on this, and it holds: `approvals.turn_id` is `NOT NULL REFERENCES turns` (`0004_stage3.sql:203`); an approval is created only by the gate's `ask` (`gate.py:147`) or `create_stall`, both inside a turn; a turn with an `ask` decision always waits (`needs_wait`, `tool_step.py:199`, `route_decide` at `graph.py:261`); the stage 2 spec has every approval pause its turn and expires one whose turn is gone (`2026-10-24-stage-2-agent-runtime-design.md`, "Waiting" and "Approvals whose turn is gone"). The roadmap's `suggest` cell for `hold` ("applied by the person in one click", `docs/roadmap.md:285`) is modeled in the stage 4-5 draft as an `ask` at the gate (I30 table, `hold` row; open point 2), so it is an approval that blocks its turn like any other; proposals (stage 3, 4, 5 kinds, `promotion`) are decided through the `Propose` call's approval while its turn waits. No spec or draft has an approval decided after its turn ended. A later plan that adds one must change this guard and sweep.
- `cancel_for_turn` otherwise unchanged. The guard is the I13 line in Produces.

**Tests (stop condition):** one shared `ApprovalStore`, as in task 1.
