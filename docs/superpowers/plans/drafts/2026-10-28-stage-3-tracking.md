# Stage 3 — Tracking Implementation Plan

> **For agentic workers:** Implement this plan task by task, in order, as `docs/implementing-plan-tasks.md` says. The plan merges through one PR for the whole branch; a task gets an early PR only when its issue says so (`AGENTS.md` rule 5). Each task lists its files, the interfaces it consumes and produces, its tests (the task's stop condition) and the checks that prove it works. Read the [stage 3 overview](../2026-10-28-stage-3-overview.md) first: it holds the shared constraints and the interface lists.

**Goal:** the app keeps one record of a project's models, versions, runs, metrics, deployments, CI runs and evaluations (spec §7):
- tracking sources (MLflow, GitHub Actions) are created through the API, each with at most one credential in the keystore;
- two adapters fill the record over REST, idempotently, keeping the last good data when a source fails; the MLflow adapter also fetches each model version's `mlops_agents/evaluation.json` (stage 5) through the tracker's artifact API;
- a sync loop runs every source on an interval and on demand;
- agents read it through the `TrackingHistory` tool and the `tracking_summary` hook.

**Branch:** `plan/stage-3-tracking`. **Consumes:** I16 (models and protocols, `tracking/contract.py`), "Shared by contracts" (the `trk` prefix, the `tracking.synced` event type, `credentials/project_secrets.py`, the tracking tables and their unique keys), all from contracts task 1; I18 (`HookRegistry`, data-summary task 1); I20 (`Handoffs.current`, proposals task 1; task 5 only); the stage 2 GitHub client, `KeyStore`, `EventLog`. **Produces:** `Tracking` (I16) and its routes from task 1 (early PR), the fake MLflow server, `TrackingHistory`, `tracking_summary`.

**Read first:** spec §7, §13 to §15 (tracking lines), overview I16 and I18; `integrations/github/api.py` (`request`, `GITHUB_API`), `agents/messaging/wakeups.py` (`start`, `_run_loop`, `close`: the model for the loop), `tests/fakes/fake_github.py` (the model for the fake server), `credentials/scrub.py` (`base_url_problem`, `error_text`, `scrub_values`).

### Task 1: The tracking service: sources, record, sync, routes

**Files:** new `backend/src/mlops_agents/tracking/__init__.py`, `tracking/constants.py`, `tracking/sources.py` (source rows, per-type settings models, credential state), `tracking/store.py` (writes and reads of the record), `tracking/service.py` (`TrackingService`, the `Tracking` implementation), `tracking/adapters/__init__.py` (`default_adapters(http, github) -> dict[SourceType, TrackingAdapter]`, empty for now), `backend/src/mlops_agents/api/routers/tracking.py`, `api/services.py` (one `tracking` field and its construction), tests under `backend/tests/tracking/`, regenerated `frontend/openapi.json`.

**Interfaces:**
- Consumes I16 in full (`TrackingSourceView`, the row models, `RunStatus`, `ModelSummary`, `EvaluationRecord`, `SyncResult` (with `evaluations`), `Page[T]`, `TrackingQuery`, `TrackingAdapter`, `Tracking`), `credentials/project_secrets.put` and `tracking_ref`, `Databases`, `KeyStore`, `EventLog`, `GitHubAuth.token()`.
- Produces `class TrackingService(Tracking)`:
  - `__init__(databases, keystore, events, adapters: Mapping[SourceType, TrackingAdapter], github_token: Callable[[], Awaitable[str | None]], clock: Callable[[], datetime] = utc_now)`;
  - the four I16 methods (`sync` starts the sync as a background task and returns; `tracking.synced` reports its end), plus `run_sync(project_id, source_id=None) -> None` (the same work, awaited: the loop and the tests use it), `set_credential(project_id, source_id, credential: str) -> TrackingSourceView` for the route, and `close()` (cancels the background syncs; registered with `stack.push_async_callback`).
- Produces the routes of I16 exactly: `GET` and `POST /api/projects/{id}/tracking/sources`; `PUT .../tracking/sources/{trk}/credential` (body `{credential: str}`, answers the source view, never echoes the value); `POST .../tracking/sync` (body `{source_id?: str}`, answers 202 with no body; a call while a source syncs is absorbed); `GET .../tracking/models` (`Page[ModelSummary]`), `.../versions?model=&source_id=` (`Page[ModelVersionRow]`), `.../runs?run_key=` (`Page[RunRow]`), `.../ci-runs` (`Page[CiRunRow]`), `.../deployments?model=&source_id=` (`Page[DeploymentRow]`), `.../metrics?run_key=&metric=&latest=` (`Page[MetricPoint]`), `.../evaluations?model=&version=` (`Page[EvaluationRecord]`). Every list route also takes `limit` (default `QUERY_LIMIT_DEFAULT`, maximum `QUERY_LIMIT_MAX`; larger is 422) and `offset`, and declares its `response_model`, so `schema.d.ts` is typed.
- Produces the event `tracking.synced {source_id, type, ok, versions, runs, metrics, ci_runs, evaluations, error}` (counts of rows the sync wrote; `error` scrubbed and cut at `ERROR_MAX_CHARS`).

**Implementation notes:**
- **Tables** are the ones contracts wrote in `0004_stage3.sql` and `tables.py` (spec §7: tracking sources, `tracked_models`, `model_versions`, `tracked_runs`, `run_metrics`, `deployments`, `ci_runs`, and the evaluations table behind `EvaluationRecord`); `last_sync` and `last_error` are on the sources table and every record table is unique on its source and key (`run_metrics`: source, run key, metric, step, time; evaluations: source, model, version). Open a Decision issue instead of editing the migration if something is missing.
- **Source settings** are validated by one model per type, `extra="forbid"`, in `sources.py`: `MlflowSettings(url: str)` (checked with `base_url_problem`, which already refuses userinfo and non-http(s) schemes; a trailing slash is stripped) and `GithubActionsSettings(repository: str, workflows: list[str] = [])` (`repository` is `owner/name`; `workflows` are workflow file names such as `ci.yml`, empty meaning all). Forbidding extra keys is what keeps a credential out of `settings`: the settings column is stored and returned as given.
- **`auth`:** `mlflow` accepts `none` or `credential`; `github_actions` accepts only `none` (I16: it uses the app's GitHub login, which the service passes to the adapter as `credential`). A `credential` source without a credential set syncs with an error "This source needs a credential" and never sends an unauthenticated request.
- **Credentials** go through `credentials/project_secrets.put(tracking_ref(project_id, source_id), value)` only (`tracking_ref` is contracts' builder; this plan writes no ref string); no other code calls `KeyStore.set` for a tracking credential. `credential_set` is `KeyStore.get(tracking_ref(project_id, source_id)) is not None`; keyring calls run in `asyncio.to_thread`. The route refuses a source that is not `auth="credential"` (422 `tracking_no_credential_needed`). The credential is never in a settings row, an event, a log line, `last_error`, an exception text or a response: `last_error` is passed through `scrub_values(text, [credential])` after `error_text`.
- **Sync of one source** (`_sync_source`):
  1. Hold the source's `asyncio.Lock`; a caller that finds it held awaits the running sync and returns without a second one (so the route and the loop can call at once).
  2. Read the credential, call `adapter.sync(source, credential, since=source.last_sync)`.
  3. An exception or `result.error` → write only `last_error` (scrubbed) and record `tracking.synced` with `ok=false`; rows and `last_sync` stay as they were (the last good data). No partial result is ever written: an adapter returns `error` with empty lists when it fails midway.
  4. Success → one transaction: upsert every row by its key (a repeated sync adds nothing and updates changed fields: run status, version aliases, CI status), make sure a `tracked_models` row exists per model, derive deployments (below), set `last_sync = clock()` and `last_error = NULL`; then record the event.
  - `run_sync(project_id, source_id=None)` runs every source of the project concurrently with `asyncio.gather` over `_sync_source`, each wrapped so one failing source never stops another. A project with no sources does nothing.
- **Deployments** (MLflow keeps only the current alias, so the app keeps the history): the current state of `(source, model, alias)` is its latest `deployments` row. For each `model -> alias -> version` of `SyncResult.aliases` that differs from the current state, insert a `DeploymentRow(from_version=<current or None>, to_version=version, seen_at=clock())`. A first sync therefore records each existing alias with `from_version=None`. An alias in the current state and absent from `SyncResult.aliases` inserts `DeploymentRow(from_version=<current>, to_version=None)` once (the state is then `None`, so a later sync adds nothing); an alias that reappears is a normal change. `ModelVersionRow.aliases` is overwritten from the same map on every successful sync.
- **Query:** `what` picks the table; filters `model`, `version`, `source_id`, `run_key`, `metric`, `since` (on the row's time column); newest first with the row key as a tie-break (so `offset` pages are stable; `models` sort by name); `limit` above `QUERY_LIMIT_MAX` is a 422 `tracking_bad_query` (the routes reject it, the tool clamps first); `offset` skips rows; `total` counts all matching rows and `truncated = total > offset + len(rows)`. `latest=true` applies to `metrics` only: one point per run and metric, the highest step (the newest time on a tie), after the other filters; with other `what` it is ignored. The result is `Page[Any]` with rows typed by `what`: `ModelSummary` (`production_version` is the version holding the alias `PRODUCTION_ALIAS` for now, null when none holds it (task 5 adds the handoff's mapping); `latest_version` the newest by creation time), `ModelVersionRow`, `RunRow`, `MetricPoint`, `DeploymentRow`, `CiRunRow`, `EvaluationRecord` (newest `fetched_at` first). `metrics` requires `run_key`; without it the service raises `DomainError("tracking_bad_query", ..., status=422)`.
- **Routes** follow `api/routers/sandbox.py` (`ProjectDep`, `ServicesDep`). Each GET path maps to one `TrackingQuery.what` (`ci-runs` to `ci_runs`). A missing source is 404 `tracking_source_not_found`; an unknown type or bad settings is 422 with the pydantic message.
- The service uses `new_id("trk")`; `tracking.synced` is already in the backend `EventType` and the frontend `PROJECT_EVENT_TYPES` (contracts).

**Tests (stop condition)** (with a fake in-test `TrackingAdapter`, a fake keystore, a temp data folder; no HTTP):
- Create: both types round-trip; `mlflow` settings with a userinfo URL, a `file://` URL or an unknown key are refused; `github_actions` with `auth="credential"` is refused; a settings body carrying `token` is refused.
- Credential: `PUT` stores in the keystore and the view flips `credential_set`; the value appears in no response, event, row or log (assert over the stored `settings`, `last_error`, `events` rows and the captured logs); an adapter error that contains the credential is stored scrubbed; the route refuses an `auth="none"` source.
- Sync: first sync writes every row type and one deployment per alias with `from_version=None`; a second identical sync adds no row; a changed alias writes one deployment with the right `from_version`; a changed run status is updated in place; a removed alias gives one deployment with `to_version=None` and the next sync adds none; an evaluation is upserted by source, model and version, and a changed payload updates it in place; an adapter that raises or returns `error` leaves rows and `last_sync` untouched, sets `last_error`, and a later good sync clears it; two sources, one failing: the other still syncs; two concurrent `sync` calls run the adapter once; a source whose adapter is missing records the error; `tracking.synced` is recorded once per source with the counts.
- Query: each `what`, rows typed by their model (`ModelSummary.production_version` by the alias `production`, null without one); every filter; `offset` pages are disjoint and complete over 120 rows; `limit` default 50, 501 gives 422; `total` and `truncated`; `latest` returns the highest step per run and metric; `metrics` without `run_key` gives 422; an unknown project is 404.
- Routes: every route of I16 incl. the 404 and 422 cases; `POST .../tracking/sync` answers 202 and `tracking.synced` follows; two quick posts run the adapter once; `npm run gen:api` leaves no diff in `frontend/openapi.json` after the regeneration commit (only `openapi.json` is committed; `schema.d.ts` is gitignored and generated).
- Full suite; `uv run ruff check`, `ruff format`, `pyright`; CI green on every job.

### Task 2: The fake MLflow server and the MLflow adapter

**Files:** new `backend/tests/fakes/fake_mlflow.py`, `backend/tests/fakes/test_fake_mlflow.py`, `backend/src/mlops_agents/tracking/adapters/mlflow.py`, `tracking/adapters/__init__.py` (the `mlflow` entry), tests `backend/tests/tracking/test_mlflow_adapter.py`.

**Interfaces:** Consumes `TrackingAdapter`, `SyncResult` and the row models (I16), the app's `httpx2.AsyncClient`. Produces `MlflowAdapter(http: httpx2.AsyncClient)` (`type = "mlflow"`), `FakeMlflowState` and `create_fake_mlflow_app(state) -> FastAPI`: an ASGI app that tests call in-process through the HTTP client's ASGI transport (no thread, no port), and that runs standalone with `python -m tests.fakes.fake_mlflow --port N` (a `main()` as in `fake_github.py`) for the e2e. Tests that need a real socket (an unreachable port) use a closed local port.

**Implementation notes:**
- **Fake server** (`/api/2.0/mlflow/...`, in-memory, request log like `FakeGitHubState.requests`):
  - `POST experiments/search`, `POST runs/search` (`experiment_ids`, `max_results`, `page_token`; ordered by start time, newest first), `GET metrics/get-history` (`run_id`, `metric_key`, `max_results`, `page_token`), `GET registered-models/search` (each model carries `aliases: [{alias, version}]` as MLflow 2.3+ does), `GET model-versions/search` (`filter=name='<model>'`), `GET registered-models/alias` (`name`, `alias`), and `GET /get-artifact` (`run_uuid`, `path`: the raw file of a run's artifact, 404 when absent, as an MLflow tracking server serves its artifacts; it sits outside `/api/2.0/mlflow/`).
  - Responses use MLflow's shapes: run `info` (`run_id`, `experiment_id`, `status`, `start_time`, `end_time` in ms and absent while running), `data` (`metrics` with the latest value, `params`, `tags` as key/value lists), `inputs.dataset_inputs`; version fields `name`, `version` (a string), `run_id`, `creation_timestamp`.
  - Paging: `page_size` on the state (default 100, tests set 2) with `next_page_token`. An unknown model or run gives MLflow's error body `{"error_code": "RESOURCE_DOES_NOT_EXIST", "message": ...}` with 404.
  - Scripting: `required_token` (`Authorization: Bearer <token>`, else 401), `fail_next: dict[str, int]` (path suffix to status, one-shot), `aliases_supported: bool` (False omits `aliases` as MLflow before 2.3).
  - Mutators the tests use: `add_experiment`, `add_run`, `finish_run`, `log_metric`, `register_version`, `set_alias`, `delete_alias`, `put_artifact(run_id, path, content: bytes)`.
- **Adapter** (`MlflowAdapter.sync`, REST with the app's client, no MLflow package, `follow_redirects=False` so a credential is never forwarded to another host, 30 s timeout, `Authorization: Bearer <credential>` only when a credential is given):
  1. `experiments/search` (paged) gives experiment ID to name.
  2. `runs/search` over all experiment IDs, newest first, at most `MLFLOW_RUN_CAP = 500` runs, paged by 100. A source with more runs keeps its 500 newest; stated in the PR description.
  3. A run is "changed" when its normalised status is `running`, or its `end_time >= since - MLFLOW_OVERLAP` (`MLFLOW_OVERLAP = 1 day`), or `since is None`. Metric history (`metrics/get-history` per metric key of the run, at most `MLFLOW_SERIES_PAGES = 10` pages of 1,000 points) is read only for changed runs; the upsert makes re-reading harmless.
  4. `registered-models/search` (paged) for the model names and `aliases`; `model-versions/search` per model for versions.
  5. Evaluations: for each version with a `run_key`, `GET /get-artifact?run_uuid=<run>&path=mlops_agents/evaluation.json` (the same client, bearer and no-redirect rules). Versions asked: with `since is None` the `MLFLOW_EVAL_CAP = 100` newest; later, those created at or after `since - MLFLOW_EVAL_WINDOW` (`MLFLOW_EVAL_WINDOW = 7 days`, since a team may write the file after registering), at most `MLFLOW_EVAL_CAP`; the upsert makes re-reading harmless. A 404 means the version has no evaluation (not an error). The body is read only up to `EVALUATION_MAX_BYTES = 262144`; it must be a JSON object with an integer `schema_version`, else that version is skipped: the file is the team's and stage 5 owns its schema, so the adapter validates only that envelope and keeps the object as `payload`. Any other non-200 status or an unreadable body skips that version and the sync still succeeds (a tracker that does not serve artifacts must not break the rest); the number skipped is logged once per sync, with no URL. A 401, 403 or a transport error is the whole-sync error as below. `EvaluationRecord.run_key` is the version's run, `fetched_at` the sync time.
  6. Mapping: `RunRow.key` is `run_id`; `status` is `RunStatus`: `RUNNING` and `SCHEDULED` to `running`, `FINISHED` to `succeeded`, `FAILED` to `failed`, `KILLED` to `cancelled`, anything else to `other`; `start` and `end` are ms to UTC datetimes; `git_commit` is the tag `mlflow.source.git.commit`; `datasets` are the `dataset_inputs` names; `params` and `tags` values are cut at 500 characters and tags at 100 per run; `MetricPoint.time` from the point's timestamp; `ModelVersionRow.run_key` from `run_id` (null when empty); `aliases` in `SyncResult` is `model -> alias -> version` from the models' alias lists, and each version row's `aliases` is the inversion of it (a model with no aliases still has an empty entry, so a removed alias is seen).
  - The `registered-models/alias` endpoint is not needed: the search response carries every alias with its version, so the adapter makes no per-alias call (the fake still serves it, as the MLflow client uses it, so a test can check it agrees with the search).
  - A server older than MLflow 2.3 sends no `aliases`: the adapter returns versions and runs and no aliases (so no deployments); not an error.
- **Errors:** every failure returns `SyncResult(versions=[], runs=[], metrics=[], aliases={}, ci_runs=[], evaluations=[], error=<plain message>)`: unreachable (`httpx2.HTTPError` through `error_text`), 401 and 403 ("The tracker rejected the credential"), any other non-200 ("MLflow answered with HTTP <n>"), a body that does not parse ("MLflow answered with data this app cannot read"). Messages never contain the URL's query, the credential or a response body.
- Windows and Linux: timestamps are integers in ms; the standalone fake binds `127.0.0.1`; nothing depends on the OS.

**Tests (stop condition):**
- The fake server (own tests): paging with `page_size=2` returns every item once; bearer auth gives 401 without the token; `fail_next` fires once; `aliases_supported=False` omits the field; the alias endpoint agrees with the model search.
- The adapter against the fake: an experiment with a finished and a running run, a model with two versions and an alias, metric series with several steps: every mapping above (status normalisation incl. `other`, ms to datetime, git commit tag, datasets, truncation of long values, alias inversion); paging across all the search calls; with `since` set after the finished run's end, history is read only for the running run (assert on the request log) and the finished run's row is still returned; `since=None` reads all histories; a bad token, a 500, an unreachable port, and a non-JSON body each give `error` with the messages above and empty lists; the credential is sent as a bearer header and never in a URL; a redirect is not followed (the fake app has a route answering 302).
- Evaluations: a version whose run has the file gives one `EvaluationRecord` with its `schema_version` and payload; a 404 gives none and no error; a body without `schema_version`, a non-object, an oversized body and a 500 on the artifact each skip only that version while the rest of the sync succeeds; with `since` recent only recent versions are asked (request log); the cap holds with 150 versions; a 401 on the artifact call is the whole-sync error.
- End to end through `TrackingService` with the fake: a first sync fills the record, `set_alias` to a new version then a second sync adds exactly one deployment with the right `from_version`, a third sync with nothing changed adds none (idempotence); the evaluation is in `Page[EvaluationRecord]` and an edited artifact updates it in place; a server shut down mid-test keeps the last good data and shows the error.
- Full suite, checks; CI green.

### Task 3: The GitHub Actions adapter

**Files:** new `backend/src/mlops_agents/integrations/github/actions.py` (the GitHub call), `backend/src/mlops_agents/tracking/adapters/github_actions.py`, `tracking/adapters/__init__.py` (the `github_actions` entry), `backend/tests/fakes/fake_github.py` (workflow runs: new state `workflow_runs: dict[str, list[dict[str, Any]]]`, `reset` clears it, one route), tests `backend/tests/integrations/test_github_actions.py`, `backend/tests/tracking/test_github_actions_adapter.py`.

**Interfaces:** Consumes the stage 2 GitHub client (`integrations/github/api.py`: `request`, `permission_missing`, `unreadable`) and `TrackingAdapter` (I16). Produces `list_workflow_runs(http, token, repo, *, created_from, limit) -> list[WorkflowRun]` and `GithubActionsAdapter(http)` (`type = "github_actions"`).

**Implementation notes:**
- `list_workflow_runs` calls `GET /repos/{repo}/actions/runs` with `per_page=100`, `created=>=<ISO date>` and `page`, through `request(..., permission="actions: read")` so a 403 or 404 becomes `github_permission_missing`, a 429 the rate-limit error. It stops at `limit` runs. `WorkflowRun` (pydantic, in `actions.py`) holds `id`, `name`, `path`, `status`, `conclusion`, `run_started_at`, `created_at`, `updated_at`, `head_sha`, `html_url`.
- The adapter reads the repository from `GithubActionsSettings`, takes the token from its `credential` argument (the service passes the app's GitHub token; none logged in gives the error "Log in to GitHub to read CI runs"), and keeps a run when the basename of `path` is in `workflows` or `workflows` is empty.
- Window: the first sync (`since is None`) reads the last `GITHUB_FIRST_SYNC_DAYS = 30` days, at most `GITHUB_RUN_CAP = 300` runs; a later sync reads runs created since `since - GITHUB_OVERLAP` (`GITHUB_OVERLAP = 1 day`), so a run that finished since the last sync is updated by the idempotent upsert.
- Mapping to `CiRunRow`: `key` is `str(id)`; `workflow` is the file basename of `path`; `status` is `RunStatus`: GitHub's `queued`, `in_progress`, `waiting`, `requested`, `pending` to `running`; `completed` with `success` to `succeeded`, with `failure`, `timed_out` or `startup_failure` to `failed`, with `cancelled` to `cancelled`, any other conclusion (`skipped`, `neutral`, `action_required`, `stale`) to `other` (`CiRunRow` has no conclusion field); `start` is `run_started_at`, else `created_at`; `duration_s` is `updated_at - start` only when GitHub's status is `completed`, else null (the billing-timing endpoint costs a call per run and is not used); `commit` is `head_sha`; `url` is `html_url`.
- Failures become `SyncResult(error=...)` with the `DomainError` message (already user-facing, token-free); the adapter never raises for a GitHub or network failure.

**Tests (stop condition):**
- The new fake route: filters by `created`, pages, honours `required_token` and `simulate_permission_error["actions: read"]`.
- The client function: pages, the `limit`, 401, 429, 403 to `github_permission_missing`, unreadable body.
- The adapter with the fake: status mapping of every case above; mapping of a completed, a failed and an in-progress run (`duration_s` null for the last); the `workflows` filter by basename; first-sync window and later-sync overlap (assert on the `created` parameter in the request log); a run that was in progress and later completed is updated, not duplicated, through `TrackingService`; no GitHub login gives the message; missing permission gives the message.
- Full suite, checks; CI green.

### Task 4: The sync loop

**Files:** new `backend/src/mlops_agents/tracking/loop.py` (`TrackingLoop`), `tracking/service.py` (`sync_interval`, `set_sync_interval`), `api/routers/tracking.py` (`GET` and `PUT /api/projects/{id}/tracking/settings`, body `{sync_interval_s: int}`, routes of I16), `api/services.py` (construct, `start`, `stack.push_async_callback(loop.close)`; the router is found by `include_routers`, so it needs no registration line), tests `backend/tests/tracking/test_loop.py`, regenerated `frontend/openapi.json`.

**Interfaces:** Consumes `TrackingService`, `WorkspaceService.list_projects`, task 2 and 3 (the adapters are registered through `default_adapters`). Produces `TrackingLoop(tracking, projects: Callable[[], Awaitable[Iterable[str]]], clock, sleep, tick_s=TICK_S)` with `start()` and `close()`, and the project setting `tracking_sync_interval_s` (default `DEFAULT_SYNC_INTERVAL_S`, minimum `MIN_SYNC_INTERVAL_S`).

**Implementation notes:**
- One app-wide task, started in `build_services` after the stores, in the shape of `WakeupService.start` and `close`: a `_stopped` flag, cancelled and awaited on `close`, a failure in one pass is logged with its traceback and the loop continues after a short sleep, `CancelledError` ends it.
- Every `TICK_S = 15` seconds it lists projects and, for each project that has sources, syncs the sources that are due: the source was never attempted, or `clock() - max(last_sync, last_attempt) >= interval`, where `last_attempt` is kept in memory by the loop per source (a failed sync leaves `last_sync` unchanged, so a source in error is retried once per interval, not every tick). A manual sync does not move `last_attempt`.
- It calls `TrackingService.run_sync(project_id, source_id)` (awaited, so a tick finishes its syncs before the next), so the per-source lock covers a manual sync and a loop sync alike. A project removed while the loop runs, or whose database cannot be opened, is skipped with one log line.
- The interval is a project setting in `project_settings`, as `MessagingSettings` stores its limits (JSON in `value`). A PUT below the minimum is 422.
- The first pass runs at startup, so a project opened after downtime catches up at once. No sync runs in tests unless the test starts the loop: `build_services` takes the loop's start from the app lifespan like the wake-ups, and the API test fixtures already use temp data folders with no sources.

**Tests (stop condition):** with a fake clock and a recording `TrackingService` double: a source never synced is synced on the first pass; a source synced less than its interval ago is skipped, and synced when the clock passes it; changing the interval takes effect on the next pass; a source in error is retried once per interval, not each tick; a project without sources and a removed project cost no call; an exception in one project does not stop the others or the loop; `close` ends the loop during a sleep and during a sync; with the real service and both fakes, a loop started on a temp app fills the record and records `tracking.synced`; the settings route round-trips and refuses an interval below the minimum. Full suite, checks, `npm run gen:api` with no diff; CI green.

### Task 5: The handoff's production alias, `TrackingHistory` and `tracking_summary`

**Files:** `tracking/service.py` (a required `handoffs: Handoffs` constructor argument and the production rule below), new `backend/src/mlops_agents/agents/tools/tracking_history.py`, `backend/src/mlops_agents/agents/hooks/tracking_summary.py`, `agents/tools/__init__.py` (one line: the tool, taking `tracking: Tracking | None`), `api/services.py` (passes the real `SqliteHandoffs` to `TrackingService`, registers the hook on the `HookRegistry` after the registry exists and before `AgentCatalog.load`, and passes `tracking` to `default_registry`), tests `backend/tests/agents/tools/test_tracking_history.py`, `backend/tests/agents/test_tracking_summary_hook.py`.

**Interfaces:** Consumes `Handoffs.current`, `HandoffView`, `ModelSpec.environments` (I20, I19; proposals task 1), `Tracking.query` (I16), `ContextHook` and `HookRegistry.register` (I18), `AgentTool`, `RiskClass.READ`. Produces the tool `TrackingHistory(what, model?, version?, source_id?, run_key?, metric?, latest?, since?, limit?, offset?)` (risk `read`) and the hook named `tracking_summary`.

**Implementation notes:**
- **Production alias** (I16): `ModelSummary.production_version` is the version holding the alias that the current handoff's `ModelSpec` for that model maps to `PRODUCTION_ENVIRONMENT` in `environments` (read through `Handoffs.current` at query time, so a new handoff applies at once; with several such aliases the first in sorted order that exists); with no handoff, or no `ModelSpec` for the model, the alias `PRODUCTION_ALIAS`; null when no version holds it. A failure reading the handoff falls back to `PRODUCTION_ALIAS` and is logged once.
- **`TrackingHistory`:** the arguments are `TrackingQuery`'s fields (`extra="forbid"`; `limit` default `QUERY_LIMIT_DEFAULT`, clamped to `QUERY_LIMIT_MAX`; `what` includes `evaluations`, whose payload is shown as compact JSON cut at 400 characters per row). It calls `Tracking.query(ctx.project_id, query)` and returns a compact text table (one line per row, key columns first, values cut at 80 characters), then a last line "N of M rows" and, when `truncated`, how to narrow (`since`, `model`, `limit`, `offset`). No rows gives "No <what> recorded yet" plus, when a source has a `last_error`, that error. It is justified as a tool because the record is in the app's database (spec §7). Bad arguments (`metrics` with no `run_key`) are `ToolFailure` with the service's message.
- **`tracking_summary`** (`name = "tracking_summary"`, `render(ctx) -> str`): reads through `Tracking.query` only. Content: the production model and version (`ModelSummary.production_version`, else the newest version; says which rule applied), its run's latest metric values (up to 10 metrics), the last 5 runs (key, status, one headline metric if any), the last 5 CI runs (workflow, status, age), and one line per source with a `last_error` or with no sync yet. Capped at `TRACKING_SUMMARY_MAX_CHARS = 3000` (a constant in the hook's module) with the cut noted. No source gives one line: "No tracking source is connected." A failure inside the hook returns one line saying the tracking summary is unavailable and never raises (I18). `render` is read-only, so running it at turn start and again when a waiting turn resumes (I18) is harmless. The hook contains no secret by construction: it reads rows only, never source settings or credentials.
- The tool names and hook name are strings other plans check (`catalog` validates `context_hooks` against `registry.names()`): they are defined once, in these two modules, and imported.

**Tests (stop condition):**

- Tool: each `what` (evaluations included) against a service holding fixture rows; the row cap and the "N of M" line; truncation advice; empty record, with and without a source error; `metrics` without `run_key` is a `ToolFailure`; the tool is `read` and the policy allows it at every level.
- Hook: a full record gives the production model by `ModelSummary.production_version`, then by newest when none is set (two cases); a record of 200 runs stays under the cap with the cut noted; no source, a source in error, and a service that raises each give their one line; the output contains none of the keystore values placed in the fixtures.
- Registered: `HookRegistry.names()` contains `tracking_summary`; `default_registry` has `TrackingHistory`.
